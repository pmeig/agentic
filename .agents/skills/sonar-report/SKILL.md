# Sonar report (run by `qa`)

`front` and `back` **write** the unit tests; `qa` **runs** them, asks SonarQube and reports. The objective is the user's rule:
coverage **100 %** (overall and new code), **0 issue** (bug, code smell), **0 vulnerability**, **0 security hotspot** left to
review, no duplication, quality gate `OK`.

## 1. Run the unit tests with coverage

1. Machine free first (`e2e-run` rule 1).
2. For each changed module (the whole project before a PR), run the unit tests **with coverage** with the module's own command
   (Vitest `--coverage`, Gradle/Maven + Jacoco, pytest-cov, `go test -cover`, `cargo llvm-cov`, `dotnet test` + coverlet, Flutter
   `--coverage`, Xcode coverage...), with the language tools as the project runs them.
3. A failing unit test is not a Sonar matter: send it to its owner (`front` or `back`) with the test, message and stack.

## 2. Is there a Sonar for this language?

1. SonarQube up (`/api/system/status` answers `UP`), project existing (`api/components/search`), module language analysed
   (`api/languages/list`, `ncloc_language_distribution` measure).
2. Language without analyser or plugin: **no Sonar check**; say so in the report, keep the local coverage figures, fall back to the
   linter and coverage tool of the language skill.
3. Sonar missing or down: never skip silently; report "Sonar not available" with the reason and ask the lead whether to start it.

## 3. Read Sonar

You need the **SonarQube URL**, a **token** and the **project key**. Take them from the project (`sonar-project.properties`, build
files, CI configuration, documented secret store). **A missing one: ask the lead** and wait; never guess a URL, look for a token
elsewhere, print or write one.

**Before asking, load the Sonar skill** (global `sonar` in `~/.agents/skills/`, then a repo skill): if one exists, follow it and do not ask.

**Once the lead has answered, write the skill so nobody asks again** (`run-and-access-skills`): a **global** skill `sonar` for the SonarQube server and where its token is read from, plus, for what is specific to the repo (project key, branch/PR scope), a **repo** skill. Never write it in `AGENTS.md` or the docs. It states how to get the quality gate:
- the SonarQube URL (from the PC and from CI runners if different);
- **where the token is read from** (Vault path and field, or environment variable) and how to read it in the same command that
  uses it. **Never write the token value** in the skill, the report or a repo;
- how to find the project key (and the known keys per project);
- the read-only calls that worked (quality gate, measures, files below 100 %, issues, hotspots) with the scope parameter
  (`pullRequest=<n>` or `branch=<name>`), and those refused for lack of privileges, with what to ask for;
- the up-check and how to start Sonar when it is down.

Keep it short, update it when the access changes, read it first next time. Never write secret values in it.

Once connected, read for the branch or PR: quality gate, coverage (overall and new code), uncovered lines per file, issues,
vulnerabilities, hotspots, duplication. Print `rule`, `file:line`, `message`, `severity`, never the raw answer. A read refused for
insufficient privileges: say so in the report and ask the lead for a token that can read it.

## 4. Exclusions: `qa` decides what Sonar must not analyse

`front` and `back` exclude nothing on their own: they **ask `qa`**, who answers with the list for their language and writes it in
`sonar-project.properties` (or the build plugin). Model: the properties generated by `pmeig/github-actions`
(`actions/java/sonar/properties`, `actions/node/sonar/setup`): reuse their keys and defaults; an existing properties file is kept
and only completed.

**Always removed, whatever the language**
- **Test files**: out of `sonar.sources`, in `sonar.tests` / `sonar.test.inclusions` (`**/*.test.ts`, `**/*.spec.ts`, `src/test/**`,
  `*Test.java`, `test_*.py`, `*_test.go`...), excluded from coverage (`sonar.coverage.exclusions`) and duplication
  (`sonar.cpd.exclusions`); the e2e folders too.
- **Build and tool configuration**: `vitest.config.*`, `jest.config.*`, `playwright.config.*`, `eslint.config.*`, generated and
  compiled output (`dist`, `build`, `target`, compiled `*.js`), migrations, generated clients.

**Per language, load the matching skill only when needed** (keys, coverage report, test files, files without behavior, standards;
each refreshes monthly), and only the module concerned: `sonar-java`, `sonar-kotlin`, `sonar-javascript-typescript`,
`sonar-python`, `sonar-go`, `sonar-csharp`, `sonar-php`, `sonar-ruby`, `sonar-swift`, `sonar-cpp`, `sonar-dart-rust`.

**Limits of `qa`'s freedom**
- A file is excluded only if it has **no logic** (no branch, loop, computation, rule). A DTO, entity, repository or helper with a
  condition, loop or business rule comes back into the coverage and is tested.
- Exclude by role (folder or name pattern), so a new file of the same role follows the same rule; never one file after a failure.
- List every pattern and its reason in `.agents/docs/team/<feature>/sonar.md` so the lead can contest it.

## 5. Report

`.agents/docs/team/<feature>/sonar.md` (replace the previous one) and a summary to the lead:

| Module | Language | Sonar | Tests | Coverage | Issues | Vulnerabilities | Hotspots | Gate |
|---|---|---|---|---|---|---|---|---|

After `qa` has validated the tests, delete `.scannerwork/` of the scanned module (skill `sonar`, "Cleanup after a local scan").

Under it, what is not clean: uncovered files with their lines, each issue (rule, `file:line`, message), each hotspot, and what was
not verified (language without Sonar, token limits).

## 6. Fixes: the owner of the code does them

Leave the loop only at **coverage 100 % and 0 issue / 0 vulnerability / 0 hotspot**. Otherwise:
1. Owner from the file path: front-end module → `front`, back-end module / SQL → `back`, test or e2e file → `qa`; a shared file →
   the agent who last changed it.
2. Send them (`SendMessage`) the exact items (file, lines, rule, message, uncovered lines). They fix with the smallest change, add
   tests or fix the code, one commit per round.
3. `qa` reruns the tests and Sonar; loop.
4. Stop and report to the lead after two identical failures of the same item, or when a fix would change a behavior or `contract.md`.

## Rules

- Never reach the objective by excluding files with logic, `// NOSONAR`, lowering a threshold or editing the quality gate. A rule
  wrong for the project is the user's call: ask the lead.
- Read-only on Sonar: no issue transition, hotspot review or quality-gate edit, unless the user asks.
- No pull request go while the Sonar objective is not reached (part of the `qa` gate with the e2e).
