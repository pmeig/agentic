# Sonar report: exclusions, `qa` decides what Sonar must not analyse

`front` and `back` exclude nothing on their own: they **ask `qa`**, who answers with the list for their language and writes it in
`sonar-project.properties` (or the build plugin). Model: the properties generated by `pmeig/github-actions`
(`actions/java/sonar/properties`, `actions/node/sonar/setup`): reuse their keys and defaults; an existing properties file is kept
and only completed.

**Always removed, whatever the language**
- **Test files**: out of `sonar.sources`, in `sonar.tests` / `sonar.test.inclusions` (`**/*.test.ts`, `**/*.spec.ts`, `src/test/**`,
  `*Test.java`, `test_*.py`, `*_test.go`...), excluded from coverage (`sonar.coverage.exclusions`) and duplication
  (`sonar.cpd.exclusions`); the e2e folders too.
- **Build and tool configuration**: `vitest.config.*`, `jest.config.*`, `playwright.config.*`, `eslint.config.*`, generated and
  compiled output (`dist`, `build`, `target`, compiled `*.js`), migrations, generated clients.

**Per language, load the matching skill only when needed** (keys, coverage report, test files, files without behavior, standards;
each refreshes monthly), and only the module concerned: `sonar-java`, `sonar-kotlin`, `sonar-javascript-typescript`,
`sonar-python`, `sonar-go`, `sonar-csharp`, `sonar-php`, `sonar-ruby`, `sonar-swift`, `sonar-cpp`, `sonar-dart-rust`.

**Limits of `qa`'s freedom**
- A file is excluded only if it has **no logic** (no branch, loop, computation, rule). A DTO, entity, repository or helper with a
  condition, loop or business rule comes back into the coverage and is tested.
- Exclude by role (folder or name pattern), so a new file of the same role follows the same rule; never one file after a failure.
- List every pattern and its reason in `.agents/docs/team/<feature>/sonar.md` so the lead can contest it.
